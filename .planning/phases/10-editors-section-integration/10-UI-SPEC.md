# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** (1) fold the standalone `editor.html`/`editor.css` surface into the shared
`_dashboard_base.html` shell as a real, data-driven 8th sidebar section (D-01/D-02/D-03);
(2) reconcile the editor's existing "Refined Street Editorial" chrome palette with
`dashboard.css`'s shell tokens WITHOUT touching the live-preview canvas, which must keep
rendering the arbitrary per-editor `--theme-*` values untouched (D-01/D-06); (3) three
named polish items — save/publish state clarity, upload feedback, mobile layout — per
CONTEXT.md D-06's explicit candidate list, nothing broader; (4) UI touch points for the
new vanity-URL copy (`nocturna-avatars.site/{slug}` replacing `.../e/{slug}`, D-04/D-05).
No behavior change (D-07): OAuth, `/editor/save`, `/editor/image`/`/editor/media`/`/editor/audio`,
self-unpublish, and the `require_editor` IDOR choke point are frozen.

**Visual sources of truth:**
- `.planning/sketches/001-dashboard-shell/` (variant A, shell chrome — unchanged, this
  phase does not touch `dashboard.css`'s existing tokens, only reuses them).
- `app/static/editor.css` (existing, as of commit `5ba161e`) — the block editor, theme
  panel, and **live-preview canvas** this phase wraps and partially retints. The preview
  canvas rules (anything driven by `--theme-*` custom properties, i.e. every `.preview-*`
  selector) are the one part of this file that must NOT be retinted — they render the
  editor's own end-user page, not admin chrome.

## Reconciliation Strategy (D-01/D-06) — the load-bearing decision of this phase

**Namespace split: retint CHROME onto `dashboard.css` tokens; leave the PREVIEW CANVAS
untouched.** `editor.css`'s current palette (`--ink`, `--ink-raised`, `--red`, `--fg`,
`--dim`, `--line`) exists for two structurally different reasons that must be separated:

1. **Admin chrome** (topbar, buttons, field inputs, block cards, picker, theme-panel
   fieldsets, upload widget, toasts) — this is the tool's OWN UI. Per D-06 "match dashboard
   look", every one of these rules is retargeted from `editor.css`'s ink/red tokens onto
   `dashboard.css`'s shipped tokens (`--color-bg`, `--color-surface`/`-2`/`-3`,
   `--color-border`/`-strong`, `--color-text`/`-muted`/`-faint`, `--color-primary`,
   `--color-danger`, `--font-sans`, `--text-*`, `--space-*`, `--radius-*`). No new chrome
   color is introduced beyond one new per-module accent (below).
2. **Preview canvas** (`.preview-col` and every `.preview-*` selector, all driven by
   `--theme-*` custom properties injected per-page) — this is a WYSIWYG rendering of the
   editor's OWN arbitrary public-page theme (any color/font the editor picks). It must
   render with **zero admin-chrome bleed**: these rules are reused **verbatim, byte-for-byte,
   unmodified** from the current `editor.css`. The editorial ink/red palette living in
   `:root` is *not* deleted — it is scoped to remain the fallback values inside
   `var(--theme-bg, var(--ink))`-style declarations only; it must never again style a
   `.btn`, `.field`, `.block-card`, `.topbar`, etc.

**Mechanical approach for the executor:** keep `editor.css` as its own file (loaded after
`dashboard.css`, same as today), but:
- Delete the chrome-facing token block at the top of `:root` (`--ink`, `--ink-raised`,
  `--paper-warm`, `--red`, `--red-on-ink`, `--red-wordmark`, `--fg`, `--dim`, `--line`,
  `--font-display`, `--font-body`, `--font-mono` as CHROME fonts) — these become
  `dashboard.css` token references instead, wherever they styled chrome.
- Keep the `--sp-*` scale as-is (see Spacing Scale — it maps 1:1 onto `dashboard.css`'s
  `--space-*` scale already, just different names; the executor may either alias
  `--sp-sm: var(--space-4)` etc., or do a global rename — planner's call, not a visual
  decision).
- Keep `--touch-min: 44px` verbatim — this is the one pre-existing, pre-approved spacing
  exception (a11y minimum touch target), same category as Phase 3's single 12px exception.
- Every `.preview-*` rule block (roughly `.preview-col` through `.preview-spotify__play`,
  plus the `@keyframes fx-*` blocks) is copied forward **without edits**.

**Result:** an editor opening `/editor` sees dashboard-blue/gray chrome (buttons, fields,
block cards, topbar) identical in feel to every other shell module, with a live preview
panel that still renders the true ink-black/red public-site aesthetic *as the editor's own
page content*, not as the tool's skin. This is the same "tool chrome vs. rendered content"
separation every code editor / CMS live-preview uses, and it directly satisfies D-06's
"match dashboard look" without breaking the preview's fidelity purpose (D-01's explicit
non-regression requirement).

## Spacing Scale

Reusing `dashboard.css`'s shipped scale verbatim as the chrome scale; `editor.css`'s
`--sp-*` values map 1:1 (same pixel values, different names today):

| Token | Value | Usage |
|-------|-------|-------|
| `--space-1` | 4px | Icon-to-label gaps (was `--sp-3xs`) |
| `--space-2` | 8px | Compact spacing, chip gaps (was `--sp-2xs`) |
| `--space-3` | 12px | Inherited Phase-3 exception, unchanged — not newly introduced here (was `--sp-xs`) |
| `--space-4` | 16px | Default field/card spacing (was `--sp-sm`) |
| `--space-6` | 24px | Section/theme-group padding (was `--sp-md`) |
| `--space-8` | 32px | Pane padding, empty-state padding (was `--sp-lg`) |
| `--space-12` | 48px | Toast bottom offset (was `--sp-xl`) |
| `--space-16` | 64px | Sticky offset for `.pane--preview`/new `.editor-subhead` height budget |

Exceptions: **44px** (`--touch-min`) — pre-existing, carried forward unchanged. This is
the editor surface's a11y minimum touch target for buttons/inputs/drag-handles (least
technical user tier, per CONTEXT.md "Specifics"). No other ad-hoc value may be introduced;
every new rule this phase adds (the `.editor-subhead`, the 3-state `.upload-state`, the
retinted `.status-badge` usage) composes only tokens in the table above.

## Typography

Chrome collapses onto `dashboard.css`'s exact closed set — no new size/weight for admin UI:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 13px (`--text-xs`) | 600 | 1.2 — field labels, `.block-type-tag`, upload state text, theme-group legends |
| Body | 15px (`--text-sm`) | 400 | 1.5 — inputs, textareas, hint text, button labels |
| Heading | 21px (`--text-lg`) | 600 | 1.2 — `.editor-subhead` title ("Editor"), modal-equivalent headers if any appear |
| Display | 32px (`--text-2xl`) | 600 | 1.2 — not used on the editor chrome itself (no page-title-scale text on this screen; the topbar wordmark is its own separate `--font-graffiti` special case, unchanged) |

**Preview canvas is explicitly exempt** from this closed set: `.preview-name`,
`.preview-tagline`, `.preview-block`, etc. size themselves off `--theme-font-scale` and the
editor's own curated font choice — that is the product feature (arbitrary page typography),
not a violation of the 4-size chrome rule. Do not attempt to clamp preview text onto
`--text-*` tokens.

Chrome font-family: `var(--font-sans)` (Inter 400/600) everywhere `editor.css` currently
uses `--font-body`/`--font-display`/`--font-mono` for CHROME elements (buttons, labels,
block-type tags, upload state, theme-group legends). The 14-font curated list and
`Space Mono`/`Space Grotesk` continue to exist **only** as available preview-font choices
inside `page.theme.font`'s `<select>` options and inside `.preview-*` rendering — never
again as the admin chrome's own type.

`--dim`) survive **only** as the fallback values inside those `var(--theme-x, --ink)`
expressions, never as a standalone chrome color again.

## Sidebar Integration (D-02/D-03)

- Promote the current bolt-on `{% if roles.is_editor %}` block in `_sidebar.html` into an
  8th entry in the `sections[]` list: `{"id": "editor", "label": "Editor", "icon": "✎",
  "accent": "var(--accent-editor)", "route": "/editor", "tier": "editor"}`.
- **Placement `[UI-SPEC decision]`: append at the end, position 8, after Settings.**
  Preserves the current bolt-on's bottom-of-nav position and its existing visual
  separator (a `border-top` on the wrapping element) — least disruptive migration, and it
  reads naturally as "your page" separated from the six operational tools + Settings.
- **Lock predicate, uniform with the other 7 (D-03):** `unlocked = roles.is_editor` for
  this entry (mirrors the existing `tier == "owner"`/`"manager"` conditions in
  `_sidebar.html`'s Jinja loop — add an `elif section.tier == "editor"` branch, or fold
  it into the same expression, resolving to `roles.is_editor`). A pure Manager/Owner
  without the editor role sees "Editor" with a 🔒, exactly like an editor sees the other 7
  locked — the additive-not-exclusive tier rule from Phase 3 D-15 applies symmetrically in
  both directions now.
- Locked "Editor" item still links to the real `/editor` route (not a disabled/no-op
  link) — clicking it as a non-editor hits `require_editor`'s 403 → shipped
  `forbidden.html` dead end. Same D-16 pattern as every other locked section.
- Visual shape: identical `.nav-item`/`.nav-item.on` classes, `--acc` inline style, ✎ icon
  glyph unchanged from today's bolt-on link. No new sidebar CSS beyond wiring the new
  accent variable through the existing `style="--acc: {{ section.accent }}"` attribute
  already used by all 7 other entries.

## Topbar Reconciliation (D-01 "Back to editor" question)

**`[UI-SPEC decision]` Remove the "Volver al editor · Back to editor" link from
`_dashboard_base.html`'s topbar entirely.** Today it renders unconditionally on every
shell page regardless of whether the viewer holds the editor role (a latent bug — a pure
Manager clicking it hits `require_editor` and 403s). Now that "Editor" is a normal,
uniformly-locked 8th sidebar entry, the link is redundant: an editor-tier user already has
a direct, always-visible, non-buggy path to `/editor` via the sidebar. Removing it
restores the topbar to its simple, page-agnostic shape (`wordmark + spacer + logout`) —
identical to what every other module already renders, no per-page conditional needed.

**Editor page's own former topbar contents** (wordmark, draft/published pill, Save/Publish,
Unpublish, owner-only Settings shortcut, logout) are **not** all deleted — they relocate:
- Wordmark + logout: now provided for free by `_dashboard_base.html`'s shell topbar — do
  not duplicate them inside `editor.html`'s content block.
- Owner-only "⚙ Ajustes · Settings" shortcut: **removed** — redundant with the shell
  sidebar's own Settings entry (owner-tier), which every owner viewing this page already
  sees in the persistent sidebar.
- Status pill + Save/Publish + Unpublish: relocate into a **new sticky sub-header specific
  to this section**, `.editor-subhead` (see Component Notes) — these three controls need
  to stay reachable while scrolling a long two-pane form, which is exactly what today's
  standalone `<header class="topbar">` gave them for free. Losing that would be a real UX
  regression, not just a chrome change, so this sub-header is the direct replacement.

## Polish Items (D-06's three named candidates — closed list, nothing broader)

### 1. Clearer save/publish states
- **Before:** a single `.label`-styled text span for draft/published, no distinct visual
  treatment for the in-flight state beyond the button's own busy label swap.
- **After:** retint onto `.status-badge` (shipped, Reminders-precedent shape):
  - Draft → `.status-badge` default (neutral `--color-border-strong` ring, muted text).
  - Published → `.status-badge.active` (success green ring/text) — reuses the exact class
    Reminders already ships for its active/paused states, zero new CSS needed for these
    two.
  - In flight (saving/publishing) → **one new modifier**, `.status-badge.pending`, amber
    ring/text using the already-declared `--color-warning` token (same value Reviews uses
    for its pending badge) — the only new CSS rule this polish item requires.
- Sits inside the new `.editor-subhead`, immediately left of the Save/Publish button, so
  state and action read as one unit (status → verb, left to right).

### 2. Upload feedback
- **Before:** `.upload-state` shows only `data-kind="error"` (red) vs. default (dim gray,
  used for both idle and any success message the JS happens to set).
- **After:** three explicit states on the same `.upload-state` element —
  `data-kind="loading"` (muted, "Subiendo… · Uploading…", no spinner asset per the
  established house convention of text-only in-progress states, see Phase 8 precedent),
  `data-kind="ok"` (success green `--color-success`, "Subido ✓ · Uploaded ✓", auto-clears
  after ~2s same as the existing toast pattern elsewhere in the app), `data-kind="error"`
  (unchanged, red). Applies uniformly to every upload widget on the page: avatar, theme
  background media, MP3 + cover art.

### 3. Mobile layout
- **Before:** `.pane-tabs` (Editar/Vista toggle) already exists and already hides ≥1024px
  — a solid foundation, not broken.
- **After (targeted, not a rebuild):** two concrete fixes —
  - `.color-grid` (theme panel's 2×2 swatch grid) collapses to 1 column below 480px — at
    2 columns on a narrow phone the swatch-field touch targets compress below the
    44px `--touch-min` floor once the label text wraps; single-column keeps every target
    at full width and height.
  - The new `.editor-subhead`'s Save/Publish + status pill row wraps onto its own line
    below the section title on narrow viewports (`flex-wrap: wrap`) rather than
    compressing the button into a truncated label — the primary CTA must never lose its
    full verb+noun label to save horizontal space (matches the house copywriting rule
    against ambiguous bare-icon buttons).

**Explicitly out of scope for this polish pass** (not named by D-06, would be scope
creep): reordering the two-pane layout itself, changing the block-type picker's grid
shape, touching the live-preview's own responsive breakpoints, or adding any new theme
control. The two-pane editor + live preview's core layout is frozen exactly as CONTEXT.md
D-01 requires ("without regressing the working two-pane editor + live preview").

## Vanity URL — UI Touch Points (D-04/D-05)

This phase's UI-visible surface of the vanity-URL capability is narrow — the mechanism
itself (Astro dynamic route + legacy redirect) is app/bot + public-site plumbing with no
new admin screen. The only admin-facing changes:
- The "Tu link · Your link" field hint text changes from `.../e/{slug}` to `.../{slug}`
  (Copywriting Contract above) — same input, same live-normalization behavior, same
  reserved-word/uniqueness validation (`core/editors_model.resolve_slug`, unchanged, D-07).
- No new field, no new confirm dialog, no new page. The existing "renaming changes your
  link" warning copy already covers the vanity-URL behavior accurately — it does not need
  new wording to also cover the legacy-redirect guarantee (the redirect is what makes old
  shared links keep working; the warning is correctly about the NEW-vs-old distinction,
  not about breakage).

## Open Questions / Flagged Assumptions

Non-interactive session (auto mode) — the following were derived from CONTEXT.md +
codebase precedent and decided here per CONTEXT.md's own delegation ("planner/UI-SPEC
decide within the decisions above"). Each is low-risk (visual/copy only) but should be
sanity-checked at the human-verify checkpoint:

1. **`--accent-editor: #f97316` (orange)** — a new per-module accent color, chosen to be
   visually distinct from all 6 existing module accents and from the locked brand red.
   Easily swapped for another hue at review time with zero structural impact (it only
   touches the sidebar left-border and the new sub-header's left-border/icon color).
2. **8th sidebar position = last (after Settings)** — CONTEXT.md left ordering to
   discretion; chosen to match the existing bolt-on's bottom placement and preserve its
   visual separator, minimizing diff/re-test surface on the 7 already-shipped entries.
3. **Removing the topbar's unconditional "Back to editor" link** — this is presented as a
   bug fix (the link currently 403s for non-editor viewers) plus a redundancy removal, not
   purely a style call. Flagging explicitly in case the owner actually valued that
   cross-page shortcut for an owner-who-is-also-editor workflow; the new 8th sidebar entry
   covers the same destination one click away instead of zero.
4. **`.toast` shape unification (bottom-right, `dashboard.css`'s shadow/position) over the
   editor's current bottom-center variant** — purely cosmetic consistency call, no
   behavior change; flagged because it's a deletion of an existing, working visual, not
   an addition.
5. **Three specific polish sub-decisions** (`.status-badge.pending` amber state, the 4th
   `upload-state` kind split into loading/ok/error/idle, `.color-grid` 1-col breakpoint at
   480px) are this researcher's concrete realization of D-06's named-but-unspecified
   candidates ("clearer save/publish states, upload feedback, mobile layout") — the
   *categories* are locked by CONTEXT.md, the *exact treatment* is this spec's proposal.
