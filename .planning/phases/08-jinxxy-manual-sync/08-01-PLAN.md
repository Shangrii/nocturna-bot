New columns (all added to the `CREATE TABLE IF NOT EXISTS` body AND to a subsequent

  - `actor_name` TEXT

1. `init_jinxxy_sync_status()` — keep the existing `CREATE TABLE IF NOT EXISTS` (extend its
   body with the 7 new columns so a brand-new DB is correct in one statement), then IMMEDIATELY
   follow it with the `ALTER TABLE jinxxy_sync_status ADD COLUMN {col} {type}` loop wrapped in
   `try/except sqlite3.OperationalError: pass  # Ya existe`, exactly as `init_reminders` does.
   BOTH code paths must ship together. `CREATE TABLE IF NOT EXISTS` alone is a silent no-op
   against every already-deployed database and will NOT add these columns (Pitfall 2). Column
   names in the ALTER statements are hardcoded string literals only — never interpolate a
   request-derived value (T-08-03).
   Extend the docstring to state that this table is Phase 8's mirror and that the ADD-COLUMN
   loop is load-bearing for deployed databases.

2. `set_jinxxy_sync_status(ok, product_count, error, *, added_count=None, updated_count=None,
   removed_count=None)` — change the write from `INSERT OR REPLACE` to
   `INSERT INTO jinxxy_sync_status (id, last_run_utc, ok, product_count, error, added_count,
   updated_count, removed_count) VALUES (1, ?, ?, ?, ?, ?, ?, ?) ON CONFLICT(id) DO UPDATE SET
   last_run_utc = excluded.last_run_utc, ok = excluded.ok, product_count = excluded.product_count,
   error = excluded.error, added_count = excluded.added_count,
   updated_count = excluded.updated_count, removed_count = excluded.removed_count`.
   This is REQUIRED: `INSERT OR REPLACE` would reset `running`, `started_at`, `source` and
   `actor_name` to their defaults on every last-run write, breaking the D-02 mirror mid-run.
   The three new parameters are keyword-only with `None` defaults so the existing keyword call
   sites in `cogs/jinxxy.py` and `tests/test_app_dashboard.py` keep working unchanged.
   This function must NOT touch `running`, `started_at`, `source` or `actor_name`.

3. New `mark_jinxxy_sync_running(source: str, actor_name: str | None = None, started_at: str | None = None) -> None`
   — ensure the row exists (`INSERT OR IGNORE INTO jinxxy_sync_status (id) VALUES (1)`), then
   `UPDATE jinxxy_sync_status SET running = 1, started_at = ?, source = ?, actor_name = ?
   WHERE id = 1`, where `started_at` defaults to `datetime.now(timezone.utc).isoformat()` when
   the argument is None. `source` is an enum-ish TEXT value; the only values this phase writes
   are `'scheduled'`, `'panel'`, `'discord'`.

4. New `clear_jinxxy_sync_running() -> None` — ensure the row exists the same way, then
   `UPDATE jinxxy_sync_status SET running = 0, started_at = NULL WHERE id = 1`. It must NOT
   clear `source` or `actor_name`: those describe the run that just finished and back the
   D-12 attribution on the last-sync card.

5. `get_jinxxy_sync_status()` — extend the explicit SELECT allowlist to
   `last_run_utc, ok, product_count, error, running, started_at, source, actor_name,
   added_count, updated_count, removed_count`. Keep it an explicit column list (repo
   convention), never `SELECT *`.

6. Add a docstring note on `get_jinxxy_sync_status` recording the D-15 detection rule for
   downstream readers: because `mark_/clear_jinxxy_sync_running` create the id=1 row on first
   boot, "never synced" is `row is None OR row["last_run_utc"] is None` — a non-None row alone
   does NOT mean a sync has ever completed.

All SQL uses `?` placeholders and the existing `with _get_conn() as conn:` idiom.
