# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** replace `/jinxxy`'s `module_stub` body with a real section — last-sync status card,
one-click Sync button, and a read-only product table — per CONTEXT.md D-01–D-17. No new visual
system: this phase is a pure composition of shipped Phase 3/5/6/7 primitives (`.mod-hdr`, `.card`,
`.stat`, `.action-proof-status`, `.tabs`-less table, `.btn`, `.status-badge`, `.toast`,
`.empty`). Zero new CSS tokens; at most 2–3 new narrow class names for the product-table row
accents, matching the "compose only" precedent PATTERNS.md set for Phase 7.

**Primary visual anchor:** the last-sync status card + Sync button pairing, positioned directly
under the section header, is the primary visual anchor and the intended first read — a Manager's
eye should land on "did it run, is it running, what happened" before anything else. The product
table sits below as secondary reference material (confirm-what-synced, not act-on-this); it never
competes with the status/button pairing for top-of-page position or for accent color (see Color).

## Interaction Contract (state machine + polling)

Binding specifics the executor needs, derived from CONTEXT.md D-01–D-12 and reusing the exact
`actionProofApp()`/`queueApp()` shape already shipped (`overview.html`, `gallery.html`):

- **Busy/disabled derivation (D-05):** the Sync button and status card busy-state come from the
  **mirror** (`jinxxy_sync_status.running`), not from this tab's own `action_queue` row — so the
  button is disabled for every Manager on the page, including one who did not click it, and
  survives a reload.
- **Two poll cadences, reusing shipped Phase-5/7 values (no new interval invented):**
  - **Own-action poll:** `1500ms`, hits `GET /api/actions/{id}` — identical to `gallery.html`'s
    `queueApp.poll()` — used only while *this tab's own click* is `pending`/`claimed`, to resolve
    the D-01/D-09/D-10 result.
  - **Ambient mirror poll:** `30000ms` — reuses `overview.html`'s existing `poll()`/`refresh()`
    cadence (the same table, `jinxxy_sync_status`, is already read there at 30s) — used to detect
    a poll- or Discord-triggered sync starting/finishing while this tab is open, so the button
    disables/re-enables without a manual reload.
  - **Elapsed-time tick:** `1000ms`, pure client-side (`Date.now() - started_at`), no network call
    — the only new interval this phase adds, and it is cosmetic only.
- **Elapsed-time format (D-07):** `{minutes}:{seconds, zero-padded to 2}` — e.g. `1:20`, `0:45`,
  `12:03`, matching the exact example already given in CONTEXT.md.
- **Voided mirror (D-06):** when `bot_heartbeat` is stale, the client MUST treat `running` as
  `false` regardless of the raw mirror value — the button re-enables and no "Sincronizando…"
  state renders, even if the row was never cleared.
- **Result rendering (D-09/D-10):** on `done`, render counts copy; on `failed`, render the D-10
  category copy (never `str(exc)`); on `done` with `result.already === true` (D-01 collision),
  render the calm "Ya se está sincronizando" copy in the **`ok`** visual state (green), never
  `failed` (red) — exact precedent: `gallery.html`'s `row.already` handling for GAL-02's
  "Ya estaba publicada." case.
- **No confirm dialog (D-16):** the Sync button's `@click` calls the enqueue POST directly; no
  `x-if="confirmRow"` gate exists for this action.

## Product Table Contract (D-13/D-14)

- **Columns (locked by D-14, `[proposed]` order/labels):** Name (linked to `checkout_url`) ·
  Price · Category · NSFW badge · Date.
- **Sort order:** `[proposed, open]` alphabetical by Name, ascending, case-insensitive. CONTEXT.md
  explicitly leaves this to planner discretion ("Exact table column set, sort order... and any
  client-side filter for the D-14 product table"); name-ascending is recommended because it is the
  most scan-friendly default for a read-only inventory check and needs no additional UI (no sort
  control required for MVP). **Flag for planner:** confirm or override before implementation.
- **Filter:** `[proposed, open]` none for this phase — D-13 explicitly scopes this to "read-only
  *display*... adds no capability"; a client-side filter is additive UI the phase does not require
  to satisfy JINX-01. If the catalog is large enough to need one, defer to a future phase rather
  than scope-creep Phase 8.
- **Data-contract limitation (D-13, must be visually honest):** `store_snapshot` holds ONLY
  `checkout_url, jinxxy_id, name, price, category, nsfw, date`. The table must never imply an
  image, description, or editor column exists — it simply omits them; no "N/A" placeholders, no
  greyed-out columns. This is enforced structurally by the column list above, not by a disclaimer.
- **NSFW badge:** reuse `.status-badge` shape; render only when `nsfw` is truthy (no badge = SFW,
  avoids table noise from an "SFW" badge on every other row).

## Open Questions / Flagged Assumptions

Non-interactive session — the following were derived from CONTEXT.md/codebase precedent rather
than confirmed live with the user. Each is low-risk (visual/copy only, does not affect the
overlap-guard engineering) but should be sanity-checked by the planner or at the human-verify
checkpoint:

1. **Sync button idle/busy labels** ("Sincronizar catálogo · Sync catalog" / "Sincronizando… ·
   Syncing…") — not given verbatim in CONTEXT.md; proposed to match the page-level-CTA
   verb+noun idiom (`reminders.html`'s "Nuevo recordatorio · New reminder") rather than Phase 7's
   row-level bare-verb idiom (Approve/Remove), since this button is the page's sole primary CTA.
2. **Section subtitle and card titles** — proposed wording only; CONTEXT.md fixed the
   status/error/empty copy but not these framing strings.
3. **Product table sort order and absence of a filter** — CONTEXT.md explicitly deferred this to
   planner discretion; this spec recommends name-ascending/no-filter as the minimal-scope default.
4. **Ambient mirror poll cadence (30000ms)** — CONTEXT.md says "reuse the Phase-5/7 values" without
   naming one specifically for this ambient case; 30000ms was selected because `overview.html`
   already polls the identical `jinxxy_sync_status`-backed endpoint at that cadence — the closest
   direct precedent available.
